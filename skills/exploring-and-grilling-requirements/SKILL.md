# 发散并拷打需求

## 核心原则

需求讨论的目标不是把问题机械地“问完整”，而是形成可证伪的功能契约：给定具体场景或状态变化，能够明确判断实现符合还是违反需求。先查明可查事实；只有会改变目标、触发、用户可观察行为、输出、状态或边界的决定才进入 Grill。Codex 负责暴露歧义、组织紧密相关的决定、生成行为校验和，并在讨论收敛时完整打印最终总体方案；用户负责选择并确认最终总体方案。

当已确认结论能够生成具体、一致的行为校验和，而且没有仍会改变功能契约的未决项时，本阶段即可收敛。实现细节没有问完不构成阻塞；两个互不兼容的实现仍可能同时声称“符合需求”时，不得收敛。

本 Skill 可以独立调用，也可以由任意上层工作流调用；它不依赖个人工作流、变更事件或特定下游阶段。普通 `brainstorming` 保留但强制禁用，任何场景都不得调用或执行；需要需求探索时使用本 Skill。

## 阶段契约

| 阶段 | 必须产出 | 完成或等待条件 |
|---|---|---|
| 查明事实 | 与议题相关的当前代码、文档和环境事实 | 足以判断需求清晰度 |
| 清晰度判定 | 目标、触发、行为、输出、状态、边界及妨碍可证伪判断的未决项清单 | 无未决项进入行为校验和；有未决项进入发散 |
| 发散 | 针对实质未决项的 2–3 个功能方向、取舍和推荐 | 用户选定或组合方向 |
| 决策包 Grill | 当前决策树中一个或多个可回答问题，不设固定数量 | 用户回答本轮问题 |
| 行为校验和 | 核心不变量、正例、反例、明确不依赖、失败时用户看到什么 | 五个字段都具体一致且来自已确认决定 |
| 最终总体方案 | 汇总全部已确认决定和行为校验和的自包含需求层方案 | 完整打印后等待用户确认 |
| 结束 | 用户已确认的最终讨论结果和需求讨论状态 | 完整展示后停止，不决定或输出后续动作 |

## 查明事实

- 先区分可查事实与需要用户取舍的决定。
- 能从代码、正式文档或环境确认的事实必须自行只读检查，不反问用户。
- 无法取得必要事实时说明访问阻塞，不猜测，也不把相关分支视为已解决。
- 当前实现只提供事实和约束，不能自动升级为需求；不得暴露发现的凭据或敏感值。

## 判断需求是否明确

查明事实后，由本 Skill 检查以下内容是否都已经显式给出、互相一致，并足以让相反实现产生不同判定：

- 功能目标；
- 输入和触发条件；
- 用户可观察行为，包括关键失败行为；
- 输出或状态变化；
- 边界和明确排除范围。

如果全部明确，直接生成“行为校验和”并进入“最终总体方案确认”，不得为了形式制造 2–3 个假方向，也不得提出不会改变功能契约的问题。用户仍必须确认最终总体方案，本阶段才完成。

如果任一项缺失、冲突，存在会改变目标、触发、行为、输出、状态或边界的用户决定，或者同一句需求仍允许互不兼容的行为都被解释为正确，才进入“发散”。输入篇幅长、已有实现或用户声称“已经很清楚”都不能代替这次判定。

## 发散

仅在清晰度判定发现实质未决项时，给出 2–3 个真正不同的功能方向。每个方向只包含核心思路、主要收益、代价或风险、适用条件；随后给出推荐及理由。

发散输出后立即等待。用户没有选定或明确组合方向前，不建立 Grill 结论，不替用户采用推荐项，也不进入任何下游动作。

## 决策包 Grill

围绕选定方向维护内部决策树。每轮重算当前 frontier：前置决定已经确定、现在可以回答的未决问题。

- 每个助手回合可以提出一个或多个问题，不设固定数量。数量以问题已经可回答、用户能够一次处理为准；问题过多时分轮，不为了遵守固定上限而拆散天然相关的问题。
- 优先把紧密相关的问题放在同一问题组中。“紧密相关”表示它们描述同一用户场景、共同决定同一行为边界，分开回答容易产生矛盾。例如同一次操作的成功条件、失败状态和重试结果可以一起提问。
- 一个独立或高复杂度问题可以单独提出；当前 frontier 中有多个适合一起回答的问题时也可以同时提出，不强制只展示一个问题组。
- 每个需要用户取舍的问题都包含可选答案、推荐答案和简短理由；成组问题要说明为什么适合由用户一次确认。
- 等待用户回答后再重算树；新暴露的行为分支加入树中。
- 用户只回答本轮一部分问题时，保留已确认答案，下一轮只重新组织仍未解决的问题。
- 事实依赖先自行查明，再提出真正需要用户决定的部分。
- 只追问会改变功能目标、触发条件、行为、输出、状态或边界的决定。
- 方法、类、模块、数据库、第三方库、调用顺序、实现日志和验收步骤留给下游阶段。
- 截止时间、权威催促或既有投入都不能替代用户决定。用户可以对当前已展示的决策包说“全部按推荐”，但这不决定尚未展示的未来分支。
- 任何影响本次功能契约的未决项都不允许标成 `Unconfirmed`、`TBD` 或默认通过；必须继续讨论。

使用这个问题组形状；按本轮实际问题数量增减条目：

```markdown
**当前问题组：<共同场景或行为边界>**

<一句话说明这些决定为什么需要一起确认>

1. **<决定一>**
   - A. <选择及影响>
   - B. <选择及影响>
   - **推荐：** <推荐项及简短理由>

2. **<问题二；按需继续增加；没有则省略>**
   - A. <选择及影响>
   - B. <选择及影响>
   - **推荐：** <推荐项及简短理由>

**请一次确认：** <例如“1A、2B”，也可以只回答其中一部分或修改任一项>
```

## 行为校验和

行为校验和是结束需求讨论前必须由本 Skill 生成并由用户明确确认的最小可证伪契约。它不是讨论摘要、实现方案或验收步骤；它必须让后续人员仅凭用户可观察事实就能区分符合与违反需求。

每个字段都必须出现：

| 字段 | 必须写清什么 |
|---|---|
| 核心不变量 | 在所有适用场景中始终成立的行为或身份关系 |
| 正例 | 一个具体输入、操作或状态变化，以及预期可观察结果；能量化时使用数值或等式 |
| 反例 | 一个看似接近但明确违反需求的结果，说明什么现象足以推翻结论 |
| 明确不依赖 | 已确认不应成为正确性前提的对象、标识、结构或偶然实现条件 |
| 失败时用户看到什么 | 失败状态、数据是否保留、能否重试，以及禁止静默发生的结果 |

- 只使用已确认决定，不把当前代码、推荐实现或技术偏好偷偷升级为需求。
- 不使用“正常工作”“正确跟随”“合理提示”等无法证伪的形容词；写出方向、距离、身份、可见状态或状态转换。
- 字段确实不适用时写 `无（原因）`，原因也必须可由用户确认；不得使用 `Unconfirmed`、`TBD` 或“由实现决定”。
- 如果填写行为校验和时暴露新歧义、字段互相冲突，或两个互不兼容的实现仍能同时满足这些字段，重新打开相应分支并发送新的决策包。
- 行为校验和及对应确认必须在本 Skill 宣布需求讨论完成前出现。后续若改变任一字段，必须重新确认。

## 最终总体方案确认

frontier 为空且行为校验和内部一致后，决策包讨论结束，但需求讨论阶段尚未完成。此时必须在一个助手回合中完整打印一份自包含的“最终总体方案（需求层）”，不能只引用先前回答、只展示最后一个决策包或只给增量摘要。

最终总体方案固定组织：

- 功能目标
- 用户场景与触发
- 总体行为
- 输出与状态变化
- 边界和明确排除范围
- 行为校验和：核心不变量、正例、反例、明确不依赖、失败时用户看到什么

“总体行为”按用户可观察的端到端顺序整合所有已确认决定；行为校验和继续保持可证伪粒度。最终总体方案不附讨论过程、被否决方案、代码缺口、实现方法、模块、存储、第三方库、正式 Plan、测试或验收步骤。

打印方案后明确输出：

```text
需求讨论状态：等待确认
最终讨论结果：<完整的最终总体方案正文>
确认请求：请确认最终讨论结果是否准确完整
```

用户修改任一内容时重新打开相应分支并继续决策包 Grill；修订后再次完整打印方案。不得把用户对单个决策包的确认、沉默、只回复“继续”或此前的概括性认可当作对最终总体方案的确认。

## 结束需求讨论阶段

只有用户明确确认“最终总体方案”后，才把本阶段标记为完成。最终总体方案已经内含行为校验和，不再要求用户分别确认两个对象。确认完成时仍要完整展示用户确认的最终讨论结果，不能只回复“已确认”或阶段状态。

无论本 Skill 是独立调用还是由上层工作流调用，都使用以下结束形状：

```text
需求讨论状态：已完成
最终讨论结果：<用户刚刚确认的完整需求层方案，内含行为校验和>
```

本 Skill 不决定或输出下一步。独立调用时，后续由用户另行要求；由上层工作流调用时，完整展示结果后把控制权交还调用方，由上层工作流依据自己的门控决定是否以及如何继续。本 Skill 完成后停止，不在同一回合执行任何下游动作。

## 常见错误

| 错误或借口 | 正确处理 |
|---|---|
| “问得越多越完整” | 只问会改变功能契约的决定；用行为校验和发现真正歧义 |
| “每轮只能问一个问题” | 每轮可问一个或多个，不设固定数量；按可回答性和用户负担组织 |
| 为减少轮次把大量无关问题塞在一起 | 紧密相关的问题成组；问题过多或关系松散时分轮 |
| “赶时间，当前和未来都采用全部推荐” | 用户只能批量确认当前已展示的问题，未展示分支仍需显式呈现 |
| 一轮机械列出整棵 frontier | 只展示当前已可回答且适合本轮处理的问题，数量由实际内容决定 |
| 代码暴露缺口，所以直接设计数据库或库 | 只保留功能事实；实现选择不进入结论 |
| 需求已经完整，仍为了执行流程强造 2–3 个方向 | 直接生成行为校验和并打印最终总体方案；发散只用于解决实质未决项 |
| 用“正常工作”代替可观察结果 | 写出正例、反例和可量化关系，直到相反实现会得到不同判定 |
| 每个决策包都确认过，所以不再总览 | 仍需完整打印自包含的最终总体方案并取得一次整体确认 |
| 最终总体方案刚打印就标记阶段完成 | 保持“需求讨论状态：等待确认”；用户明确确认后才能完成 |
| 方案已确认，所以替调用方决定后续动作 | 完整展示已确认结果并停止；独立调用等待用户，上层工作流调用则交还其门控 |
| 用 `Unconfirmed` 把问题传给下游 | 继续 Grill，直到问题被明确决定 |

## 红旗

- 清晰度判定没有未决项，却仍制造替代方向或无关问题
- 已进入发散且用户尚未选方向，就出现“最终结论”
- 为问题数量设固定上限，导致天然相关的问题被机械拆开
- 一轮问题多到用户难以一次处理，或把不能由同一场景解释的问题强行混组
- 未展示的未来问题被“全部按推荐”自动决定
- 行为校验和缺少任一必填字段，或只写“正常”“正确”“合理”等不可证伪描述
- 正例、反例和明确不依赖仍允许相反行为或相反状态变化同时通过
- 最终总体方案没有完整重述全部确认决定，只引用旧消息或只展示增量
- 最终总体方案包含未由用户确认的方法、模块、存储、库、正式 Plan 或验收步骤
- 最终总体方案尚未得到明确确认，却出现“需求讨论状态：已完成”
- 确认完成时没有完整展示最终讨论结果，只输出状态或增量摘要
- 本 Skill 在结束需求讨论的同一回合执行下游动作，或替独立调用和上层工作流写死后续步骤
- 仍有 `Unconfirmed`、`TBD` 或未经用户确认的行为校验和却准备交接

出现任一红旗时，回到当前阶段并恢复相应等待门禁。

# 发散并拷打需求

## 核心原则

先查明可查事实并判断需求是否已经明确。目标、触发、行为、输出、状态和边界都完整一致时，直接整理确认结论；存在实质未决项时才发散不同方向并逐项 Grill。Codex 负责查明事实和判断是否仍有未决项，用户负责做决定并确认结论。

个人工作流路由到本 Skill 后，不使用普通 `brainstorming`。用户说 `skip-brainstorm` 只排除普通 `brainstorming`，不跳过本 Skill。

## 阶段契约

| 阶段 | 必须产出 | 完成或等待条件 |
|---|---|---|
| 查明事实 | 与议题相关的当前代码、文档和环境事实 | 足以判断需求清晰度 |
| 清晰度判定 | 目标、触发、行为、输出、状态、边界及冲突的未决项清单 | 无未决项进入收敛；有未决项进入发散 |
| 发散 | 针对实质未决项的 2–3 个功能方向、取舍和推荐 | 用户选定或组合方向 |
| Grill | 当前决策树中一个前置条件已满足的关键问题 | 用户回答该问题 |
| 收敛 | 仅包含已确认功能结论的摘要 | 用户确认摘要 |
| 结束 | 已确认结论、阶段完成状态和下一阶段 | 输出后停止，不在同一回合进入下游阶段 |

## 查明事实

- 先区分可查事实与需要用户取舍的决定。
- 能从代码、正式文档或环境确认的事实必须自行只读检查，不反问用户。
- 无法取得必要事实时说明访问阻塞，不猜测，也不把相关分支视为已解决。
- 当前实现只提供事实和约束，不能自动升级为需求；不得暴露发现的凭据或敏感值。

## 判断需求是否明确

查明事实后，由本 Skill 检查以下内容是否都已经显式给出、互相一致且不需要新的用户决定：

- 功能目标；
- 输入和触发条件；
- 用户可观察行为，包括关键失败行为；
- 输出或状态变化；
- 边界和明确排除范围。

如果全部明确，直接进入“收敛与确认”，不得为了形式制造 2–3 个假方向，也不得提出不会改变功能契约的问题。用户仍必须确认“确认结论”，本阶段才完成。

如果任一项缺失、冲突或存在会改变目标、触发、行为、输出、状态或边界的用户决定，才进入“发散”。输入篇幅长、已有实现或用户声称“已经很清楚”都不能代替这次判定。

## 发散

仅在清晰度判定发现实质未决项时，给出 2–3 个真正不同的功能方向。每个方向只包含核心思路、主要收益、代价或风险、适用条件；随后给出推荐及理由。

发散输出后立即等待。用户没有选定或明确组合方向前，不建立 Grill 结论，不替用户采用推荐项，也不进入 Spec。

## 逐问 Grill

围绕选定方向维护内部决策树。每轮重算当前 frontier：前置决定已经确定、现在可以回答的未决问题。

- 每个助手回合只问 frontier 中一个最高影响的问题。
- 问题包含可选答案、推荐答案和简短理由。
- 等待用户回答后再重算树；新暴露的行为分支加入树中。
- 事实依赖先自行查明，再提出真正需要用户决定的部分。
- 只追问会改变功能目标、触发条件、行为、输出、状态或边界的决定。
- 方法、类、模块、数据库、第三方库、调用顺序、实现日志和验收步骤留给下游阶段。
- 截止时间、权威催促、既有投入或“全部按推荐”都不能替代逐项用户决定。
- 任何影响本次功能契约的未决项都不允许标成 `Unconfirmed`、`TBD` 或默认通过；必须继续讨论。

使用这个问题形状：

```markdown
**当前问题：<一个需要决定的问题>**

- A. <选择及影响>
- B. <选择及影响>

**推荐：** <推荐项及简短理由>
```

## 收敛与确认

frontier 为空后，输出“确认结论”，仅组织：

- 功能目标
- 输入与触发条件
- 已确认行为
- 输出或状态变化
- 边界和明确排除范围

不附讨论过程、被否决方案、代码缺口、实现建议、测试或验收步骤。请用户确认这些结论是否完整准确；用户修改任何结论时重新打开相应分支并继续逐问。

## 结束需求讨论阶段

只有用户明确确认“确认结论”后，才把本阶段标记为完成。不要询问是否调用 `writing-specs`，不要创建变更事件，也不要在同一回合进入下游阶段。

在已开启的个人工作流中，使用以下固定交接形状：

```text
个人工作流：已开启
当前阶段：需求讨论
阶段状态：已完成
确认结论：<仅包含已经确认的功能结论>
下一阶段：建立变更事件
下一步：继续个人工作流，由 managing-change-ledger 登记变更事件；事件建立后再进入 writing-specs
```

个人工作流保持开启，不需要用户再次说“开启”。本 Skill 完成后停止；后续由 `using-personal-development-workflow` 按既定顺序推进 `managing-change-ledger → writing-specs`。

如果本 Skill 是在个人工作流之外由用户单独调用，只输出已确认结论和“需求讨论已完成”，不自动调用 `managing-change-ledger` 或 `writing-specs`；后续动作由用户另行要求。

## 常见错误

| 错误或借口 | 正确处理 |
|---|---|
| “赶时间，直接采用全部推荐” | 推荐不能转移决策权；仍一次问一个问题 |
| 一轮列出整棵 frontier | 只问当前最高影响的一个问题 |
| 代码暴露缺口，所以直接设计数据库或库 | 只保留功能事实；实现选择不进入结论 |
| 需求已经完整，仍为了执行流程强造 2–3 个方向 | 直接整理确认结论；发散只用于解决实质未决项 |
| 结论已确认，所以立即写 Spec | 在个人工作流中先结束本阶段；下一阶段必须建立变更事件，之后才进入 Spec |
| 用 `Unconfirmed` 把问题传给下游 | 继续 Grill，直到问题被明确决定 |

## 红旗

- 清晰度判定没有未决项，却仍制造替代方向或无关问题
- 已进入发散且用户尚未选方向，就出现“最终结论”
- 一个助手回合包含两个或更多问题
- 未展示的未来问题被“全部按推荐”自动决定
- “确认结论”包含方法、模块、存储、库、计划或验收步骤
- 变更事件建立前出现 `# Spec`
- 本 Skill 在结束需求讨论的同一回合创建变更事件或调用 `writing-specs`
- 仍有 `Unconfirmed` 或 `TBD` 却准备交接

出现任一红旗时，回到当前阶段并恢复相应等待门禁。

## 简例

需求已经完整明确时，查明事实后直接展示“确认结论”并等待用户确认，不制造替代方向。

需求存在实质未决项，或用户在个人工作流之外明确要求“先发散再 Grill”时，先自行查明可查事实，再给出三种功能方向并等待选择。用户选择方向 B 后，只问：

> **当前问题：同步失败后，批注在界面中应保持什么状态？**
>
> - A. 保留并显示可重试状态
> - B. 自动隐藏，后台继续处理
>
> **推荐：** A；用户能看到失败且数据不会被误认为已删除。

回答后才提出下一项决定。全部决定解决后，展示确认结论并停止等待；用户在后续回答中明确确认该摘要后，输出“需求讨论已完成”。个人工作流中的下一阶段是建立变更事件，事件建立后才进入 `writing-specs`。

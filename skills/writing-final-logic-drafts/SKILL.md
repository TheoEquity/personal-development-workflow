# 编写最终逻辑稿

## 核心原则

把已经验收通过的真实功能整理成一份能让读者在脑中还原运行过程的轻量说明。它不是 Spec、Plan、架构文档或验收报告，也不深入函数、类和文件层面。

## 使用前提

只接受总控提供的同一 `change_id`、当前不可变 `spec_ref`、`plan_ref`、`test_ref`、`code_ref` 和已经由唯一 validator 判定全部通过的 `evidence_ref`。验收失败、存在未执行项、引用无效，或材料与实际代码互相冲突时停止；不得用 Spec 或 Plan 中的预期行为冒充最终行为。

## 输出合同

固定路径为 `logic/<change_id>.md`。对话中展示的候选稿与最终保存稿使用同一份完整 Markdown，依次只有以下槽位：精确 H1、必填的 `## 功能逻辑`，以及可选的 `## 注意事项`。候选稿直接使用正式标题和章节，不另加“候选”“canonical”标题或章节外的编号清单：

```markdown
# <change_id> 最终逻辑稿

## 功能逻辑

[先说明核心机制是什么、又不是什么；再按真实发生顺序说明用户触发、系统处理、页面或状态结果，以及理解完整流程所必需的顺序、层级、重复触发和清理行为。]

## 注意事项

[仅记录正文之外确实需要提醒的少量事项；没有时省略本节。]
```

正常粒度以这类说明为准：核心思路不是锁住原 Tooltip，而是制作视觉快照；用户让临时浮层正常出现，按下快捷键后系统先扫描真正可见的浮层，再复制到保留位置、尺寸和视觉内容的冻结层；快照不可交互，位于产品页之上、批注层之下，并可进入截图。冻结完成后才选择画框工具，因此原浮层消失后仍能在快照上批注。再次触发、按 Escape、切换页面、退出模式、加载失败或页面卸载时清除快照。

这是功能级的连续逻辑，不是一句话摘要。只写理解该功能所必需的事实；不强制拆成核心思路、用户流程、内部顺序、数据关系、异常路径、支持范围和副作用等固定栏目，也不穷举无关边界。

## 形成步骤

1. 从不可变引用读取最终 Spec、已评审 Plan、实际代码和通过的验收报告。
2. 以实际代码与验收事实为准核对最终行为；发现契约冲突时停止并交回总控。
3. 按输出合同形成候选稿，不写测试步骤、实际结果清单、证据、代码符号或文件清单。
4. 在对话中完整展示候选稿，等待用户确认；未确认时不保存、不提交，也不完成事件。
5. 确认后只保存到当前项目 Spec Vault 的 `logic/<change_id>.md`，把控制权交回总控。不得修改 `change.md`、SQLite、工作流游标或任何代码。

## 常见错误

| 错误 | 修正 |
|---|---|
| 把逻辑稿压成一句总结 | 按真实顺序讲清触发、处理、结果和必要的清理行为 |
| 套用八个固定栏目 | 使用一个连续的 `功能逻辑` 主体，只有确有需要才加 `注意事项` |
| 照抄 Spec 或 Plan | 对照最终代码与通过验收的事实，只写已经实现并验证的行为 |
| 写成代码导读或测试报告 | 删除函数、类、文件和逐项证据，只保留功能级逻辑 |
| 验收通过后直接完成事件 | 先形成并确认 canonical 逻辑稿，再把控制权交回总控 |
| 候选稿使用普通标题或章节外清单 | 候选稿直接使用 `# <change_id> 最终逻辑稿` 和 `## 功能逻辑` 的正式结构 |

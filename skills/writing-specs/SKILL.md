# 编写 Spec

## 核心原则

根据已经明确的需求，直接编写或修改系统功能契约，并对当前代码做一次有边界的只读扫描，附上“可能的影响范围”。Spec 的行为章节定义系统必须表现成什么样；“可能的影响范围”的唯一规范性定义见下文对应章节。

判断一项内容是否属于行为契约：更换内部实现后，只要该要求仍然成立，它就属于 Spec 的规范性章节。方法、类、模块、调用顺序和数据结构由落盘 Plan 维护；它们出现在“可能的影响范围”时只表示扫描线索，不成为行为要求。

## 材料身份与测试稿子节点

个人工作流中，本 Skill 必须接收总控提供的 `change_id`，不得自行生成、替换或推断材料身份。Spec 固定保存为 `specs/<change_id>.md`，版本由 `specs/<change_id>.md@<full-vault-commit-sha>` 唯一定位。

Spec 经用户确认、保存并形成 `spec_ref` 后，**REQUIRED SUB-SKILL:** 使用 `writing-test-drafts` 生成 `tests/<change_id>.md`。调用时原样传入同一 `change_id`、已确认 Spec，以及用户提供的操作步骤、流程和预期结果。用户未提供时，也必须调用该子 Skill，由它根据已确认 Spec 和可验证的系统入口生成测试验收操作；不得要求用户补写每一步，也不得由本 Skill 复制测试稿 grammar。

本次“既有功能与流程影响”只用于 Spec 与 Plan 的编码前影响确认。调用测试稿子 Skill 时，不得把影响表本身解释成新增回归范围或自动生成额外测试项；测试稿仍只依据已确认的规范性行为和用户提供的验收步骤形成。不修改 `writing-test-drafts` 的合同、模板或 validator。

Spec 和测试稿都形成有效引用后，本阶段才算完成并进入 Plan。`writing-specs` 仍只拥有行为契约；`writing-test-drafts` 仍是测试操作、测试项 ID 和验收报告可执行语法的唯一拥有者。

## 内容契约

Spec 只组织以下内容：

- **功能目标**：系统需要提供什么能力。
- **输入与触发条件**：谁或什么在什么情况下触发功能。
- **行为规则**：系统在对应条件下必须做什么。
- **输出与状态变化**：外部能够观察到的结果。
- **边界**：适用范围、异常输入、重复执行和明确不包含的行为。
- **既有功能与流程影响**：与本需求直接相交的既有可观察行为或业务流程，以及本次保持、兼容扩展或明确改变的结论。
- **可能的影响范围**：基于指定代码 Git SHA 的只读扫描结果，仅列可能受影响的方法、文件、调用方或公共资源。

每条行为规则写清楚触发条件、系统必须产生的行为和可观察结果。失败、重试或补偿属于功能契约时，写进对应行为规则或边界。

## 既有功能与流程影响

完成规范性行为和边界后、扫描代码影响范围前，检查本需求是否与已经存在的功能、业务流程、外部接口行为或兼容承诺直接相交。只记录存在直接依赖、共享状态、共用入口/输出或行为承诺的项目，不遍历所有历史功能。

“当前行为”必须来自已确认的现有 Spec、接口合同、可复现运行事实或其他用户指定的正式资料；不能根据方法名、示例或记忆猜测。写无直接影响结论前，也必须对本需求会使用的入口、状态、输出和明确共享资源做一次有边界的核对。无法验证当前行为或无法判断交点时，停止等待确认，不能用无影响结论消除不确定性。

使用以下固定表格：

| impact_id | 既有功能或流程 | 当前行为 | 与新需求的交点 | 影响结论 | Spec 处理 |
|---|---|---|---|---|---|
| I-001 | 批注同步 | 同一批注只对应一个 Issue | 新同步策略复用原映射 | 保持不变 | 无需修改 |

`impact_id` 使用 `I-001`、`I-002` 等稳定编号。更新同一份 Spec 时保留已有编号；新增项取下一个未使用编号；删除后不得复用，也不得因排序变化而重编号。

`影响结论` 只允许：

- `保持不变`：现有可观察行为必须继续成立。
- `兼容扩展`：新增能力不得破坏既有入口、状态或结果。
- `明确改变`：现有行为会改变，变化已经同步写入本 Spec 的规范性行为、输出、状态或边界。

`Spec 处理` 只允许 `无需修改` 或 `已写入规则或边界`。`明确改变` 必须选择 `已写入规则或边界`，不能只在影响表中描述变化。

不存在直接关联项时不伪造表格行，整个章节只写这一条固定结论：

```markdown
- 结论：未发现与本需求直接关联的既有功能或流程。
```

本章与“可能的影响范围”分层：本章是已经确认的行为与流程兼容合同；后者只是基于代码 SHA 的非确定性代码发现入口。若当前行为、交点或用户可观察变化仍不确定，必须停在 Spec 阶段请求确认，不得交给 Plan 决定，也不得用“需要核对”的代码线索代替行为结论。

## 可能的影响范围：规范性边界

本节是“可能的影响范围”含义的唯一规范来源。该范围不是行为契约、实现承诺或验收条件，只是提供给后续 `writing-plans` 的代码发现入口。每一项必须使用“可能修改”“可能新增”或“需要核对”，不得写成“一定修改”“必须新增”或已经确认的实现方案。Plan 必须依据更完整的当前代码检查自行收窄、扩展或纠正候选范围；这种纠正不修改行为契约。

## 扫描可能影响范围

完成行为章节后，以 Spec 用词、用户给出的入口和当前代码事实为线索，只读检查最近的功能入口、主要调用方、共享方法与类型、公共资源、配置以及相关测试。扫描到能够给 `writing-plans` 提供起点时停止，不无理由遍历整个仓库。

- 只写已经找到路径或符号证据的对象；找不到时不得凭记忆虚构。
- 记录实际扫描的代码基线 `<repository>@<code-git-sha>`。
- 扫描发现此前遗漏的共享入口、状态或输出可能构成新的既有行为/流程直接交点时，必须返回“既有功能与流程影响”补充或确认；行为结论仍不明确时停止，不得只留下代码线索后继续发布 Spec。
- 对象与 Spec 行为有直接关联但是否修改尚不能确定时，标记 `需要核对`。
- 可能需要改变现有对象时标记 `可能修改`；当前未找到承载位置、Plan 可能需要新增对象时标记 `可能新增`。
- 不在本阶段决定方法签名、调用顺序、数据结构、依赖、重试实现或日志实现。

个人工作流中如果代码基线 SHA 无法验证，停止并说明缺口，不形成正式 Spec 引用。个人工作流之外没有代码仓库或基线时，保留该章节并明确写“未扫描：缺少可验证代码基线”，不得猜测影响对象。

## 编写要求

- 使用用户已经确认的需求和用户指定的正式资料作为依据。
- 修改现有 Spec 时，保留未受本次需求影响的规则，只修改受影响内容。
- 使用“必须”“不得”“当……时”等可以明确判断的表达，避免“正常处理”“符合预期”等模糊描述。
- 规范性行为章节使用“必须”“不得”；可能影响范围按“可能的影响范围：规范性边界”执行。
- 正式保存前，在对话框展示完整 Spec；用户确认后再写入文件。
- 个人工作流中固定写入总控提供的 `specs/<change_id>.md`；个人工作流之外按用户指定或项目既有的位置保存，没有明确位置时只在对话框给出完整 Spec。

## 输出格式

```markdown
# Spec：<功能名称>

## 功能目标

<系统必须提供的能力>

## 输入与触发条件

- <输入、事件或触发状态>

## 行为规则

### 规则：<规则名称>

当：

- <触发条件>

系统必须：

- <系统对外表现出的行为>

结果：

- <外部可以观察到的输出或状态>

## 输出与状态变化

- <返回内容、界面变化、外部系统变化或持久状态>

## 边界

- <异常、重复执行、适用范围或明确排除的行为>

## 既有功能与流程影响

| impact_id | 既有功能或流程 | 当前行为 | 与新需求的交点 | 影响结论 | Spec 处理 |
|---|---|---|---|---|---|
| I-001 | <已存在的功能或流程> | <本需求前的可观察行为> | <与新需求的直接交点> | <保持不变 / 兼容扩展 / 明确改变> | <无需修改 / 已写入规则或边界> |

<!-- 没有直接关联项时删除表格，只保留：
- 结论：未发现与本需求直接关联的既有功能或流程。
-->

## 可能的影响范围（非行为契约）

- 代码基线：`<repository>@<code-git-sha>`
- 说明：本节来自只读代码扫描，只表示可能范围，不表示一定需要修改，也不作为验收条件。

| 可能影响对象 | 当前路径 | 可能的影响类型 | 判断依据 |
|---|---|---|---|
| `<方法、文件、调用方或公共资源>` | `<已确认路径>` | `<可能修改 / 可能新增 / 需要核对>` | `<与哪条 Spec 行为相关以及当前代码证据>` |
```

## 示例

下例只演示已经确认“保持不变”后的行为写法；不得把示例中的“复用原映射”等事实照抄到尚未确认的需求。

```markdown
### 规则：保持批注与 Issue 的唯一映射

当：

- 系统首次同步一条具有稳定批注 ID 的批注。

系统必须：

- 创建一个对应的 GitLab Issue。
- 后续修改和重试必须继续作用于原 Issue。
- 同一批注不得产生第二个 Issue。

结果：

- 该批注始终最多对应一个 GitLab Issue。
```

## 内容边界

| 内容 | 归属 |
|---|---|
| 功能行为、输入、输出、状态和边界 | Spec |
| 既有功能、业务流程及兼容承诺的保持、扩展或明确改变 | Spec 的“既有功能与流程影响”章节 |
| 初步代码扫描得到的非确定性影响线索 | Spec 的“可能的影响范围”章节 |
| 确定的文件、方法、接口、调用顺序、技术兼容处理和实施步骤 | 落盘 Plan |
| 点击、命令、检查动作和逐步预期 | 测试稿 |
| 实际结果、通过状态和证据 | 验收稿 |

Spec 不设置 `Current Implementation Gap`、`Unconfirmed Items`、`Failure and Recovery`、`Acceptance Links` 或状态转移矩阵等独立章节。

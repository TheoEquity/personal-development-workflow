# 编写 Spec

## 核心原则

本 Skill 只定义系统应该表现出的行为，不写实现步骤。调用者必须明确传入同一 CE 的 `change_id` 和 `profile=light` 或 `profile=full`；direct 不调用本 Skill，也不得为了复用模板生成空 Spec。

两种 profile 共用同一个 Skill、同一个 `specs/<change_id>.md` 路径和同一套行为表达，不建立两套工作流：

| profile | 适用情况 | 材料强度 |
|---|---|---|
| `profile=light` | 新增或改变正式行为，但范围明确、实现简单、风险低 | 一份短 Spec；无正式 Plan 和测试稿门禁 |
| `profile=full` | 行为模糊、存在重要方案选择，或触及架构、公共契约、数据、安全等高风险边界 | 完整行为契约、影响分析、代码基线和正式测试稿 |

profile 缺失、不是 `light/full`，或需求仍存在会改变行为的未决项时停止，不自行猜测。

## 身份与保存

个人工作流中必须使用总控提供的 `change_id`，固定保存为 `specs/<change_id>.md`，正式版本用 `specs/<change_id>.md@<full-vault-commit-sha>` 定位。不得自行生成或替换身份。

正式保存前在对话中完整展示 Spec；按当前 `review_mode` 取得确认或满足自动推进条件后再保存。修改现有 Spec 时保留未受影响的规则。

## Light profile

`profile=light` 只回答以下内容：

- **要解决的问题**：为什么需要这次改变。
- **触发条件**：在什么输入、事件或状态下触发。
- **期望行为**：系统对外必须表现成什么样。
- **本次范围**：明确包含和不包含什么。
- **完成条件**：怎样可以独立验收。
- **可选兼容边界**：必须保持不变的行为或关键兼容边界；没有直接相关项时省略，不生成空章节或表格。

Light 的固定模板：

```markdown
# Spec：<功能名称>

## 要解决的问题

<问题>

## 触发条件

- <输入、事件或状态>

## 期望行为

- <可观察行为>

## 本次范围

- 包含：<范围>
- 不包含：<非目标>

## 完成条件

- <可验证结果>

<!-- 仅在有直接相关项时增加：
## 必须保持不变

- <既有行为或关键兼容边界>
-->
```

Light 明确不执行 Full 的材料门禁：

- 不强制既有功能影响表；
- 不扫描代码 SHA，也不要求“可能的影响范围”；
- 不生成正式测试稿，不调用 `writing-test-drafts`，不生成 `test_ref`；
- 不生成正式 `plan_ref`；确需拆步骤时由工作流在 `.local` 维护运行态任务清单。

这些省略不免除实现前理解现有行为、实现后实际验证以及保存真实 `code_ref`；它们只是不进入短 Spec 和正式材料链。

## Full profile

`profile=full` 使用以下规范性章节：

- 功能目标；
- 输入与触发条件；
- 行为规则；
- 输出与状态变化；
- 边界；
- 既有功能与流程影响；
- 可能的影响范围（非行为契约）。

每条行为规则写清触发条件、系统必须产生的行为和可观察结果。使用“必须”“不得”“当……时”等可判断表达，避免“正常处理”“符合预期”。

### 既有功能与流程影响

只记录与本需求存在直接依赖、共享状态、共用入口/输出或兼容承诺的既有行为，不遍历全部历史。当前行为必须来自当前有效 Spec、接口合同、可复现事实或用户指定的正式资料；`change.md` 历史摘要只能作为调查线索，不能覆盖当前有效行为。

使用固定表格：

| impact_id | 既有功能或流程 | 当前行为 | 与新需求的交点 | 影响结论 | Spec 处理 |
|---|---|---|---|---|---|
| I-001 | <功能或流程> | <当前可观察行为> | <直接交点> | <保持不变 / 兼容扩展 / 明确改变> | <无需修改 / 已写入规则或边界> |

`impact_id` 使用 `I-001` 起的稳定编号；删除后不得复用，也不得因排序变化而重编号。

- `保持不变`：既有可观察行为继续成立。
- `兼容扩展`：新增能力不得破坏既有入口、状态或结果。
- `明确改变`：变化必须同步写入规范性规则或边界，Spec 处理必须为 `已写入规则或边界`。

没有直接关联项时不伪造表格，只写：

```markdown
- 结论：未发现与本需求直接关联的既有功能或流程。
```

当前行为或交点不确定时，必须停在 Spec 阶段，不得交给 Plan 决定。既有行为合同与“可能的影响范围”严格分层，不得用后者的代码线索替代行为结论。

### 可能的影响范围

在指定的精确 `<repository>@<code-git-sha>` 上做有边界的只读扫描，只列有路径或符号证据的候选对象。该章节只为 Plan 提供发现入口，不是行为契约、实现承诺或验收条件。

候选类型只使用：`可能修改`、`可能新增`、`需要核对`。代码基线无法验证时停止，不形成正式 Full Spec 引用。

### Full 模板

```markdown
# Spec：<功能名称>

## 功能目标

<能力>

## 输入与触发条件

- <输入、事件或状态>

## 行为规则

### 规则：<规则名称>

当：

- <条件>

系统必须：

- <行为>

结果：

- <可观察结果>

## 输出与状态变化

- <结果或状态>

## 边界

- <异常、重复执行、适用范围或非目标>

## 既有功能与流程影响

<固定表格或唯一无影响结论>

## 可能的影响范围（非行为契约）

- 代码基线：`<repository>@<code-git-sha>`

| 可能影响对象 | 当前路径 | 可能的影响类型 | 判断依据 |
|---|---|---|---|
| `<对象>` | `<路径>` | `<可能修改 / 可能新增 / 需要核对>` | `<证据>` |
```

## Full 的测试稿子节点

只有 `full` Spec 经确认、保存并形成 `spec_ref` 后，**REQUIRED SUB-SKILL:** 使用 `writing-test-drafts` 生成 `tests/<change_id>.md`。原样传入同一 `change_id`、已确认 Spec 以及用户提供的操作步骤、流程和预期结果；用户未提供时由该子 Skill 根据行为契约和可验证入口形成测试稿。

影响表本身不得被解释成新增测试范围。Full 只有在 `spec_ref` 与 `test_ref` 都有效后才完成 Spec 阶段并进入正式 Plan。

## 内容边界

| 内容 | 归属 |
|---|---|
| 用户可观察行为、输入、输出、状态与边界 | Spec |
| 既有行为兼容结论、代码影响扫描 | 仅 Full Spec |
| 文件、方法、调用顺序、数据结构和实施步骤 | Full Plan；Light 的 `.local` 任务清单 |
| 点击、命令、检查动作和逐步预期 | Full 测试稿或轻量验证清单 |
| 实际结果和证据 | 验收记录 |

Spec 不设置 `Current Implementation Gap`、`Unconfirmed Items`、`Failure and Recovery`、`Acceptance Links` 或状态转移矩阵等额外固定章节。

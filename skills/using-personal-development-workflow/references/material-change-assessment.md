# 材料变更评估

当已有正式 Spec 或 Plan 可能因失败、修正、追加或外部事实而变化时，先确定真实语义影响，再决定修改规模。评估不是强制小改：局部影响做定点修改；多个核心行为、整体实现路线或任务依赖图已经失效时，允许合理的大幅修改。

## 何时使用

在任何材料、代码或阶段变化之前执行本评估，只要存在直接相关的正式 Spec/Plan，并出现以下任一事实：

- 当前事件的 TDD、自测或验收失败；
- 当前 `in_progress` 事件内需要修正已登记范围的需求理解；
- 后续追加内容、新增行为或范围扩展与既有正式事件直接相关；
- 已完成事件之后出现需求变化或外部 Bug；
- reviewer、代码调查或基线漂移表明当前正式材料可能失效。

这里的“阶段变化”是指根据上述新事实回退、推进或改写已有正式事件的责任阶段。正常的新事件登记不是材料变更：需求讨论确认后仍可登记并进入 `writing_spec`；但若新事件与旧正式材料直接相关，写入新 Spec、测试稿、Plan 或代码前必须完成本评估。

没有直接相关正式材料的新需求按正常流程建立新 Spec，不制造空评估。不得仅因为事件位于同一项目，就把无关事件选作比较基线。

## 正式输入

### 当前事件

从活动游标绑定的总账事件读取当前 `spec_ref` 与 `plan_ref`，按引用中的完整 Git SHA 读取不可变内容。失败事实来自可复现的 TDD/自测事实或已由唯一 validator 校验的验收报告；必要代码上下文必须与正式引用和受测代码版本一致。

### 后续追加或新事件

需求讨论先确定本次变化与哪些既有行为或实现直接相关。已完成事件保持不可变，只读取这些相关事件的正式引用作为比较基线；新变化登记新事件并形成自己的 Spec、测试稿和 Plan，不得回写旧事件。

新事件尚无 Plan 时，Plan 结论注明“本事件尚无 Plan；仅评估相关旧 Plan 的可复用与失效范围”，不得伪造本事件的 `Task N`。

任一引用无效、身份不一致、无法读取，或事实不足以区分局部与结构性影响时，保持当前阶段并报告缺口，不先编辑材料。

## 评估输出

先输出两份独立结论：

```text
材料变更评估
- Spec：<无需修改 / 局部修改 / 结构性修改>
  - 基线：<当前 spec_ref 或明确相关的旧 spec_ref>
  - 位置：<具体章节或 impact_id；无需修改时写“无”>
  - 依据：<新事实与正式 Spec 的对照>
  - 预计动作：<保留 / 定点修改 / 结构性修改 / 在新事件中继承并改变>
  - 明确保留：<不受影响的规则、边界或 impact_id>
- Plan：<无需修改 / 局部修改 / 结构性修改>
  - 基线：<当前 plan_ref、明确相关的旧 plan_ref 或“本事件尚无 Plan”>
  - 位置：<具体章节或 Task N；无需修改时写“无”>
  - 依据：<新事实、正式 Plan 与必要代码事实的对照>
  - 预计动作：<保留 / 定点修改 / 结构性修改 / 在新事件中重新规划>
  - 明确保留：<不受影响的兼容性结论、关键分支或 Task N>
阶段状态：等待用户确认评估
下一步：确认本次材料变更评估
```

每个结论都必须给出基线、位置、依据、预计动作和明确保留项。“无需修改”也必须说明材料为何已经覆盖当前事实，不能只写结论。

## 修改规模

`无需修改 / 局部修改 / 结构性修改` 分别适用于：

| 结论 | 判定 | 确认后的材料动作 |
|---|---|---|
| 无需修改 | 正式材料已经准确覆盖目标行为和实现路线 | 不创建新版本，不更新对应引用 |
| 局部修改 | 只有有限行为、边界、影响项、兼容性结论、关键分支或任务失效 | 只修改确认位置，保留其他章节、稳定 ID 和任务编号 |
| 结构性修改 | 多个核心行为、整体实现路线或任务依赖图失效，局部补丁会产生矛盾、重复或错误顺序 | 说明局部补丁为何不足和明确保留项后，允许合理的大幅修改 |

修改规模只能由语义影响决定。改动行数、文件数和主观百分比不能单独证明局部或结构性修改。“尽量小改”不能成为保留错误材料的理由。

## 用户确认门禁

每次材料变更评估输出后都立即停止，等待用户明确确认，包括 Spec 与 Plan 均为 `无需修改` 的组合。

有效确认必须针对刚展示的版本，明确同意 Spec 与 Plan 两份结论，或明确说“确认本次材料变更评估”。评估展示前的预授权、只回复“继续”不构成确认，“你自己决定”“别再问”也不能替代本次确认。

确认前不得修改、保存或提交 Spec/Plan；确认前不得修改生产代码或测试代码；确认前不得移动 `current_stage`、启动实现器、创建代码 commit、更新 `code_ref`，也不得把评估写成新的 SQLite 状态或正式材料。

用户要求调整评估时，继续使用同一组不可变引用修订评估并再次等待确认。只有当前对话明确确认的版本，才能作为后续 `writing-specs`、`writing-lean-plans`、Plan reviewer、`adopt-plan` 或 TDD 路由的范围输入。旧对话、持久游标、既有 Plan 批准和旧执行授权都不能恢复本次确认。

## 确认后的路由

- Spec 与 Plan 均无需修改：保持引用不变，进入当前事实对应的最早责任阶段；实现偏差通常返回 `tdd_coding`。
- 只有 Plan 需要变化：保留 Spec，只修改或重建确认范围内的 Plan，重新独立 review 并调用 `adopt-plan`。
- Spec 需要变化：先修改、确认并提交 Spec，更新 `spec_ref`；随后只重新评估新 Spec 实际影响的 Plan 部分。第二轮仍输出 Spec 与 Plan 两份结论：Spec 以新 `spec_ref` 为基线记录“无需追加修改”及保留项，Plan 则基于新 Spec 重新判断范围。旧 Plan 评估不能跨 Spec 版本直接复用。
- 后续追加或已完成事件之后的变化：建立新事件，在新材料中按确认结论继承有效规则并表达变化，不修改旧事件。

局部修改保存前以评估所用正式引用为基线检查 Git diff。评估范围外的大段删除、整份替换、Task 全部重建或无理由重编号必须拒绝并回到评估。结构性修改可以产生大 diff，但必须与确认的重构范围和明确保留项逐项一致。

任一材料需要修改时，代码门保持关闭。Spec 先确认并更新引用，Plan 再独立 review、提交并由 `adopt-plan` 采用；只有材料门重新打开后，才按新材料重新满足 TDD 和执行授权。

评估确认本身不授权编码或 commit。若 Spec、Plan、基线、worktree 或 Task 范围发生变化，即使仍在同一对话，旧执行授权也失效；材料重新采用后必须重新展示执行门禁。两份材料均无需修改时，只有仍能证明当前对话中的原合同精确覆盖同一 Plan、worktree 和 Task 范围，才可继续使用；否则重新取得授权。确认后先完成一个责任阶段路由并停止，不在同一轮直接改代码。

如果评估开始时已经存在材料修改前产生的代码改动，将其冻结但不自动删除；在材料门重新打开前，不得继续修改、提交或更新 `code_ref`。采用新材料后，以新 `spec_ref`/`plan_ref` 和实际 worktree diff 重新核对；只有差异仍落在确认范围内并重新满足 TDD 与授权门禁时才能继续。

## 快速参考

| 事实 | 评估动作 |
|---|---|
| 小型实现偏差，Spec/Plan 已覆盖 | 两份结论可为无需修改，但仍展示并等待确认 |
| Plan 漏步骤，行为契约正确 | Spec 无需修改；Plan 局部修改 |
| 一个行为边界变化 | Spec 局部修改；确认新 Spec 后定点重审 Plan |
| 多个核心行为或任务依赖图失效 | 结构性修改；说明局部补丁不足和保留项 |
| 已完成事件后的相关追加 | 旧材料只读；新事件继承并表达变化 |
| 无直接相关旧材料 | 不执行本评估，走正常新需求流程 |

## 常见错误与停止信号

| 错误或压力 | 必须采取的动作 |
|---|---|
| “只是小 Bug，直接回 TDD” | 先输出两份结论并等待确认 |
| “赶时间，整份重写更快” | 先按语义判定范围；局部影响拒绝无关重写 |
| “尽量小改，所以不能大改” | 核心行为或依赖图失效时允许结构性修改 |
| “旧事件最相关，直接回写” | 已完成事件不可变；创建新事件 |
| “同项目的旧 Plan 都可参考” | 只读取需求结论或用户明确选择的直接相关事件 |
| “评估在旧对话确认过” | 当前对话重新展示并等待确认 |
| “先改代码，稍后补材料” | 代码门关闭；先完成材料确认、引用更新和 Plan 采用 |

出现引用缺口、事实歧义、未确认评估、评估外 diff 或材料顺序被绕过时立即停止，只报告当前事实和一个下一动作。

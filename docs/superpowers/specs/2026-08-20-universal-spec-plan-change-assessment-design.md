# Spec 与 Plan 统一变更评估门禁设计

## 背景

个人开发工作流已经在当前 `in_progress` 事件发生 TDD、自测或验收失败时执行“返工影响审查”，并分别判断 Spec 与 Plan 是否需要修改。现有规则仍有两个缺口：

- 后续追加内容、范围扩展或已完成事件之后的新变化会进入新事件，但没有统一要求先对照相关既有正式 Spec/Plan 评估继承、保留和改变范围。
- 当前只有结构性重写明确要求用户确认；局部修改或无需修改的评估结果可能未经确认就进入后续材料或代码动作。

现有 Plan 合同还把开发基线固定为远程分支最新 SHA。大多数新开发适合使用远程基线，但重新规划或开发到一半继续时，正确基线可能是尚未推送的本地 commit。工作流需要在创建或重写 Plan 前同时展示本地与远程候选，由用户选择，而不是把远程最新 SHA 当作唯一合法来源。

本设计把返工专用审查扩展为统一的“材料变更评估门禁”。目标不是强制小改，而是先用正式材料判断真实语义影响，再选择与影响相匹配的修改规模。局部影响采用定点修改；多个核心行为、整体实现路线或任务依赖图确实失效时，结构性修改是正常结果。

## 目标

- 任何基于已有正式 Spec/Plan 的修正、追加或扩展，在修改材料前先完成影响评估。
- Spec 与 Plan 分别判断 `无需修改 / 局部修改 / 结构性修改`，避免一个材料的变化自动扩大成两份材料重写。
- 每次评估都先完整展示并等待用户确认；确认前不修改 Spec、Plan 或代码，也不移动到后续责任阶段。
- 修改规模服从语义影响，不用行数、文件数或主观百分比限制合理的大改。
- 局部修改保留评估范围外的规则、`impact_id`、兼容性结论和 `Task N`。
- 结构性修改说明局部补丁为何不足，并明确仍然保留的有效内容。
- 已完成事件和其正式引用保持不可变；后续变化继续登记新事件。
- 不新增正式材料类型、SQLite 字段或工作流阶段。
- 创建或重写 Plan 前同时解析本地与远程候选基线，默认推荐远程，但允许选择可复现的本地 commit SHA。
- 用户只回复“继续”而未另行指定时，采用已经展示的唯一远程候选。

## 非目标

- 不要求所有变化都做小补丁。
- 不把多个核心行为或整体实现路线已经失效的情况强行压成局部修改。
- 不扫描或继承与当前变化没有直接关系的全部历史事件。
- 不修改已完成事件的 Spec、Plan、代码引用或验收报告。
- 不用工作区草稿、聊天记忆或文件时间替代正式 Git 引用。
- 不让影响评估替代需求讨论、Spec 确认、Plan 独立评审或 `adopt-plan`。
- 不增加“评估中”持久阶段；等待确认是当前对话门禁。
- 不把未提交工作区状态伪装成 Git SHA，也不静默把脏工作区内容纳入 Plan 基线。
- 不要求用户每次手填完整 SHA；工作流负责解析并展示候选。

## 统一触发条件

存在下列任一情况，并且本次动作需要沿用、修改或对照已有正式 Spec/Plan 时，必须先执行材料变更评估：

- 当前事件的 TDD、自测或验收失败可能需要修改材料或代码。
- 当前 `in_progress` 事件内，用户确认需要修正已登记范围内的需求理解。
- 用户提出新增行为、范围扩展或后续追加内容，且存在直接相关的既有正式事件。
- 已完成事件之后出现需求变化或外部 Bug，需要建立新事件并判断哪些既有行为、兼容承诺或实现路线仍然成立。
- reviewer、代码调查或远程基线漂移发现当前正式材料可能失效。

没有任何直接相关正式材料的新需求仍按正常流程从需求讨论和新 Spec 开始，不制造空评估。不得仅因为事件位于同一项目就自动选择它作为比较基线；相关旧事件必须由当前需求结论、已登记关系或用户明确选择确定。

## 正式输入

### 当前事件返工

从活动游标绑定的总账事件读取当前 `spec_ref` 与 `plan_ref`，按完整 Git SHA 读取不可变内容。验收失败使用已校验报告的失败事实；TDD、自测、reviewer 或基线漂移使用可复现事实和必要代码上下文。

### 后续追加或新事件

已完成事件保持不可变。需求讨论先确定本次变化与哪些既有行为或实现存在直接关系；只读取这些相关事件的正式引用作为比较基线。新事件后续产生自己的 `specs/<new-change_id>.md` 和 `plans/<new-change_id>.md`，不得回写旧事件材料。

如果新事件尚未形成 Plan，则 Plan 评估明确写“尚无本事件 Plan；仅评估相关旧 Plan 的可复用与失效范围”，不能伪造本事件的 `Task N`。正式 Plan 仍在 `writing_plan` 阶段按已确认的新 Spec 创建并评审。

任一引用无效、身份不一致、无法读取或事实不足以区分局部与结构性影响时停止并报告缺口，不先编辑材料。

## 评估输出合同

评估必须先输出两份独立结论：

```text
材料变更评估
- Spec：<无需修改 / 局部修改 / 结构性修改>
  - 基线：<当前 spec_ref 或相关旧 spec_ref>
  - 位置：<具体章节或 impact_id；无需修改时写“无”>
  - 依据：<新事实与正式 Spec 的对照>
  - 预计动作：<保留 / 定点修改 / 结构性修改 / 在新事件中继承并改变>
  - 明确保留：<不受影响的规则、边界或 impact_id>
- Plan：<无需修改 / 局部修改 / 结构性修改>
  - 基线：<当前 plan_ref、相关旧 plan_ref 或“本事件尚无 Plan”>
  - 位置：<具体章节或 Task N；无需修改时写“无”>
  - 依据：<新事实、正式 Plan 与必要代码事实的对照>
  - 预计动作：<保留 / 定点修改 / 结构性修改 / 在新事件中重新规划>
  - 明确保留：<不受影响的兼容性结论、关键分支或 Task N>
阶段状态：等待用户确认评估
下一步：确认本次材料变更评估
```

每个结论都必须包含基线、位置、依据、预计动作和明确保留项。“无需修改”也要说明现有材料为何已经覆盖当前变化；不能只写结论。

## 修改规模判定

### 无需修改

正式材料已经准确覆盖目标行为和实现路线，问题只是实现偏差、测试环境或无需改变材料的事实更新。对应材料不创建新版本、不更新引用。

### 局部修改

只有有限行为、边界、影响项、兼容性结论、关键分支或任务失效，材料整体结构和大多数内容仍然成立。确认后只修改评估列出的位置，并保留未受影响的章节、稳定 ID 和任务编号。

### 结构性修改

多个核心行为、整体实现路线或任务依赖图已经失效，局部补丁会造成矛盾、重复或错误顺序。评估必须说明局部修改为何不足，列出需要重构的范围以及仍然有效、应当保留的内容。用户确认后允许合理的大幅修改，不以“小改优先”为理由保留错误设计。

修改规模只能由语义影响决定。代码或 Markdown 的行数、文件数和主观百分比不能单独证明局部或结构性修改。

## 用户确认门禁

每次材料变更评估输出后都立即停止，等待用户明确确认。该门禁适用于三种结论的全部组合，包括 Spec 与 Plan 均为“无需修改”。

确认前不得：

- 修改、保存或提交 Spec/Plan；
- 修改生产代码或测试代码；
- 移动 `current_stage` 到评估建议的责任阶段；
- 启动实现器、创建代码 commit 或更新 `code_ref`；
- 把评估结果写成新的 SQLite 状态或正式材料。

用户要求调整评估时，基于同一正式引用修订评估并再次等待确认。只有用户确认的版本才能作为后续写作 Skill、Plan reviewer、`adopt-plan` 或 TDD 路由的范围输入。持久游标和旧对话不能恢复本次确认授权。

## Plan 基线选择门禁

### 触发时机

每次创建新 Plan 或因返工、远程漂移、开发中途调整而重写 Plan 时，在代码调查和写入候选 Plan 之前执行基线选择。既有 Plan、旧对话选择、持久游标或当前 checkout 不能自动成为新 Plan 的基线。

### 候选发现

工作流先从项目配置确定实现仓库，再解析并展示：

- **本地候选**：与当前工作流直接相关的实现 Worktree 或分支 `HEAD`，包含绝对 Worktree、分支或 detached 状态、40 位完整 commit SHA，以及工作区 `clean/dirty` 状态。没有绑定 Worktree 时展示当前实现仓库 checkout 的 `HEAD`；存在多个相关候选且无法唯一确定时全部列出，不自行选择。
- **远程候选**：目标 remote 与 branch 的最新 40 位完整 SHA。新 Plan 无法从项目配置、当前分支 upstream 或用户已确认上下文唯一确定目标 remote/branch 时，先请求用户确定目标，不猜测 remote 默认分支。远程候选使用只读远端查询取得；仅有本地 remote-tracking ref 时不能声称它是远程最新值。

候选卡固定显示来源、定位信息、完整 SHA 和状态：

```text
Plan 基线候选
- 本地：<absolute-worktree> | <branch-or-detached> | <40位 SHA> | <clean/dirty>
- 远程：<remote>/<branch> | <40位 SHA>
默认选择：远程
下一步：选择本地、远程或明确的其他已有 commit SHA；只回复“继续”将采用远程候选。
```

远程查询失败、目标歧义、本地 SHA 无法解析或候选不属于配置中的实现仓库时停止，不创建 Plan。

### 选择语义

- 用户明确选择远程、选择所展示的远程 SHA，或者在候选卡之后只回复“继续”时，采用远程候选。
- 用户明确选择本地候选、其定位信息或完整 SHA 时，采用该本地 commit；它可以尚未推送，也不要求等于远程最新 SHA。
- 用户指定另一个 SHA 时，只接受配置实现仓库中可解析的 40 位 commit，并展示其来源与可达性后再次确认。
- 用户的沉默、普通编码指令或未展示候选时的“继续”不能代替本次基线选择。

未提交修改不属于任何 SHA。本地候选为 `dirty` 时，候选 SHA 只代表 `HEAD`：工作流必须明确列出脏内容被排除；如果用户希望把这些内容纳入基线，需要另行取得范围准确的本地 commit 授权、形成 commit 后重新解析候选。不得从脏 Worktree 直接调查并把结果归因给旧 `HEAD`。

### 选择后的验证

选择远程基线时，才对所选 remote/branch 执行受限 fetch，更新对应本地 remote-tracking ref并解析 SHA。fetch 后 SHA 必须等于候选卡中已确认的值；如果远程在等待选择期间移动，展示新旧 SHA 并重新执行选择门禁，不能静默采用新 SHA。

选择本地基线时不执行远程相等性门禁。写 Plan 前重新解析所选 commit，并验证相关 Worktree 或分支仍指向该 SHA；定位对象已经移动时重新展示候选。代码调查必须读取所选 commit 的 Git tree 或一个 `HEAD` 精确等于该 SHA 的干净隔离 Worktree，不得混入当前脏工作区。

无论选择哪种来源，候选 Plan 都在 `## 开发基线` 中记录：

```text
base_source: <remote | local>
base_locator: <remote/branch | absolute-worktree@branch-or-detached>
base_sha: <40位完整 commit SHA>
```

远程来源继续把 remote 和 branch 作为独立 reviewer 输入；本地来源把配置仓库、Worktree/分支定位、commit 是否已推送和脏改动排除结论作为 reviewer 输入。Plan writer、独立 reviewer 和后续执行器必须使用同一基线 Git tree。

### 开发入口

Plan 采用后不再次把基线强制改成远程最新 SHA。开发入口按 `base_source` 分流：

- `remote`：核对所选 remote/branch，执行既有受限 fetch 和 SHA 漂移门禁，一致后从该 SHA 创建或确认隔离 Worktree。
- `local`：验证 commit 仍存在且实际 Worktree `HEAD` 等于所选 SHA；允许复用符合要求的干净相关 Worktree，或从该 SHA 创建隔离 Worktree，不与远程最新 SHA 比较。

任一来源发生 SHA 漂移时，代码门保持关闭并返回 Plan 基线选择；不能先开发后 rebase，也不能沿用旧 Plan 的批准。

## 确认后的动作

- Spec 与 Plan 均为“无需修改”：保持引用不变，进入当前事实对应的最早责任阶段；实现问题通常返回 `tdd_coding`。
- 只有 Plan 需要变化：保留 Spec，仅修改或重建确认范围内的 Plan 内容，重新独立评审并调用 `adopt-plan`。
- Spec 需要变化：先修改并确认 Spec、提交并更新 `spec_ref`；随后只重新评估新 Spec 实际影响的 Plan 部分。Plan 的旧评估不能跨 Spec 版本直接复用。
- 后续追加或已完成事件之后的变化：建立新事件；在新事件材料中按确认结论继承有效规则并表达变化，不修改旧事件。

局部修改保存前必须以评估所用正式引用为基线检查 Git diff。评估范围外的大段删除、整份替换、Task 全部重建或无理由重编号必须拒绝并回到评估。结构性修改可以产生大 diff，但仍须与确认的重构范围和保留项逐项一致。

## 与现有流程的关系

- 现有“返工影响审查”改为统一材料变更评估的一个触发场景，不保留两套相互漂移的合同。
- 需求讨论仍决定新需求、范围扩展和外部 Bug 的行为边界及事件身份。
- `writing-specs` 与 `writing-plans` 只接收已确认评估列出的修改位置和保留范围；不得自行扩大修改面。
- Plan 仍需独立 reviewer `Approved`，并由 `managing-change-ledger adopt-plan` 机械校验和采用。
- 任一材料需要修改时，既有“先改稿后改码”顺序门禁继续生效。
- 验收报告、测试稿、最终逻辑稿和事件完成合同保持不变。

## 修改位置

### `using-personal-development-workflow`

- 把“返工影响审查”重构为统一材料变更评估合同。
- 在内部失败、需求追加/范围扩展、新事件继承、reviewer/代码调查和远程基线漂移入口调用同一合同。
- 增加每次评估都先展示并等待用户确认的硬门禁。
- 将确认后的评估范围原样传给 `writing-specs`、本次 `writing-plans` 调用与后续路由。
- 保留事件边界、正式引用、代码门和授权规则。
- 在每次 Plan 创建或重写之前发现并展示本地/远程候选；只回复“继续”时选择远程。
- 按 `base_source` 分流 Plan 评审输入和开发前 SHA 验证，不再无条件要求远程相等。

### `using-personal-development-workflow/references`

- 将详细评估模板、修改规模判定和确认门禁放入独立 reference，入口 Skill 只保留触发条件、读取要求、路由摘要和必读链接。
- `execution-contract.md` 继续只定义实现授权，不复制材料评估字段。

### 契约测试

- 增加当前事件内部失败场景，验证每种评估结论都在移动游标或修改材料前等待确认。
- 增加局部追加场景，验证只修改确认位置并保留其他规则、`impact_id` 和 `Task N`。
- 增加结构性变化场景，验证说明局部补丁不足后允许大改，同时核对明确保留项。
- 增加已完成事件后续变化场景，验证新建事件、只读旧材料并形成新材料，不回写旧事件。
- 增加无相关旧材料场景，验证正常进入新需求流程，不伪造影响评估。
- 增加压力场景：时间紧、已有投入和负责人要求直接重写时，仍先评估、展示并等待确认。
- 增加 Plan 基线候选场景：同时展示相关本地 `HEAD`、dirty 状态和远程最新 SHA；只回复“继续”时选择远程。
- 增加本地继续开发场景：选择未推送的本地 commit 后不执行远程相等性门禁，Plan writer、reviewer 与执行器使用同一 Git tree。
- 增加脏 Worktree 场景：旧 `HEAD` 只能作为排除脏改动后的候选；不得把未提交内容归入该 SHA。
- 增加候选漂移场景：远程或本地定位在确认后移动时重新展示并确认，不静默换基线。

## 完成标准

- 内部失败与后续追加内容使用同一材料变更评估合同。
- 每次评估都在任何材料、代码或阶段变化之前展示并等待用户确认。
- Spec 与 Plan 的修改规模分别按语义影响判定。
- 局部影响只产生确认范围内的定点修改；结构性影响能够合理产生大改，并保留仍有效内容。
- 已完成事件保持不可变，后续变化拥有新的事件和材料身份。
- 没有新增正式材料、SQLite 字段或工作流阶段。
- 安装版 Skill 与可发布仓库副本通过相同契约测试并保持一致。
- 每次 Plan 创建或重写前都展示本地和远程候选基线；单纯回复“继续”采用远程候选。
- 本地 commit 可以作为 Plan 和开发基线且不要求等于远程最新 SHA；未提交内容不会被错误归入 SHA。
